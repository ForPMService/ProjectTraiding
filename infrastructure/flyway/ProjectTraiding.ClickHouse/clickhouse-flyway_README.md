# База рыночных рядов ProjectTraiding (ClickHouse) — проект миграций

Таблицы столбцовой базы для хранения исторических рыночных рядов Московской биржи.
Реализует решения из «Архитектуры хранения рыночных рядов v0.4» и опирается на
фактические схемы ответов и объекты передачи данных (DTO) контура
`ProjectTraiding.Moex`. Отдельный проект миграций рядом с проектом PostgreSQL.

> **Версия 3.** Числовые типы выровнены по DTO (требование двоичной вставки).
> Время — `DateTime64(3, 'Europe/Moscow')`. Рыночное время названо `source_time`.
> **Режим разведки данных:** ключевые столбцы обязательны, неключевые — `Nullable`
> (пустую ячейку источника храним как есть, разбираем потом). На таблицах выключено
> окно дедупликации вставок `non_replicated_deduplication_window` миграцией `V002`.

## Единые правила

- **Движок** — `MergeTree`. Обычная вставка, без «вставить или обновить».
- **Разбиение** — по году от столбца времени (`toYear(...)`).
- **Ключ сортировки** — инструмент, затем время; плюс измерение, где оно есть
  (`clgroup`, `metric`, `alert_type`).
- **Время** — `DateTime64(3, 'Europe/Moscow')`.
- **Обнуляемость** — ключевые столбцы (входящие в `ORDER BY`, а для свечей ещё
  `begin`) обязательны; все неключевые — `Nullable`.
- **Дедупликация повторов** — `non_replicated_deduplication_window = 0` на каждой
  таблице; выключено миграцией `V002`, защиту от повторов даёт удаление диапазона перед загрузкой.
- **Именование** — префикс `moex_`.

## Типизация: столбец повторяет поле DTO

Тип SQL-столбца совпадает с типом поля DTO (требование двоичной вставки):
`double? → Float64`, `int? → Int32`, `long? → Int64`, `string? → String`/
`LowCardinality(String)`, `DateTime? → DateTime64(3, 'Europe/Moscow')`. Объекты
неоднородны, одноимённые поля в разных рядах бывают разного типа: `val_b`/`val_s` у
сделок акций — `Float64`, у стакана — `Int64`; `vol` у сделок акций — `Int32`, у
фьючерсов — `Int64`; объёмы заявок `put_vol*` — `Int32`, обороты `put_val*` —
`Float64`; на cancel-стороне `cancel_vol_b` — `Int32`, а `cancel_vol_s`/`cancel_vol`/
`cancel_orders` — `Int64`. Каждая таблица выверена отдельно.

## Политика пустых значений (режим разведки)

Парсер уже устроен правильно: пустую ячейку источника он оставляет полем `null` в
объекте и **никогда не подменяет значением по умолчанию**. Эта база переносит ту же
дисциплину в хранилище.

- Неключевые столбцы — `Nullable`: законная пустота источника (нет сделок — нет
  средневзвешенной; одна сделка — нет стандартного отклонения; пустой `reference`)
  хранится как `NULL`, чтобы потом отличить тихий рынок от дефекта загрузки.
- Ключевые столбцы (`ORDER BY` + `begin` у свечей) — обязательны. Парсер их от пустоты
  **не** охраняет, поэтому это делает писатель: строку с пустым ключевым полем
  (`secid`, время, `clgroup`/`metric`/`alert_type`) он отвергает явной ошибкой.
- **Запрет:** писатель нигде не подменяет `null` нулём или пустой строкой. Иначе
  законный пропуск станет неотличим от настоящего нуля, и последующая проверка
  пропусков потеряет смысл. `null` остаётся `null` от ответа биржи до запроса.

Проверка пропусков выполняется не построчно при вставке, а после загрузки: на уровне
диапазона сверяется число строк с ожиданием из торгового календаря, а оставшиеся
`NULL` трактуются как законная пустота источника. Перезапись дефектного диапазона —
это «удалить диапазон по разделу/условию, затем вставить заново».

## Стратегия записи и идемпотентность повторов

- **История** пишется синхронными крупными вставками по логическому диапазону
  (одна единица «инструмент-ряд-год» = одна вставка). Это идеальный для движка размер
  части, ошибка локальна.
- **Журнал истины** — PostgreSQL: знание «какие диапазоны загружены» живёт в
  управляющей базе.
- **Отложенная вставка (`async_insert`) для истории не используется** — это режим
  реального времени и мелких потоков.

Повтор безопасен, потому что запись идёт в пустой диапазон:

```
проверка наличия строк в диапазоне → ALTER TABLE ... DELETE диапазона → INSERT
```

Журнал дедупликации вставок выключен миграцией `V002`. `ReplacingMergeTree` остаётся
и защищает случаи, где пишут два контура или приём получает повторный снимок.

## Что подтвердить на живых данных

1. **Зона времени** — что биржа отдаёт московское время.
2. **Сжатие — вторым шагом** (кодеки delta/Gorilla позже, по умолчанию LZ4).
3. **Соответствие DTO при его изменении** — типы выверены по текущему репозиторию.

## Чего здесь нет

Пятиминутные свечи (копия `moex_candles_1m` под именем `moex_candles_5m`, если грузятся
от биржи), сырой стакан реального времени, рассчитанные признаки (широкие
версионированные таблицы фазы исследования).

## Порядок применения

`flyway -configFiles=flyway.conf migrate` создаёт все таблицы (пустые таблицы бесплатны).
При желании можно оставить в `migrations/` только нужные сейчас файлы и добавлять
остальные позже. Под гипотезу v0 первоочередные — свечи, статистики сделок и стакана,
а для серебряного фьючерса ещё открытый интерес.
