# Европейский приёмник — промпт № 1

Независимый Generic Host на `net11.0`, SDK `11.0.100-rc.1.26425.128`,
`LangVersion=preview`. Российское приложение в `backend/` не изменено.
Скомпилированы управление пользовательской сессией, bounded-очередь,
постоянный каталог каналов, автономный бот владельца и нативная пересылка.
Функциональные проверки, авторизация, запуск приложения и развёртывание
в этом цикле не выполнялись. Следующие промпты не реализованы.

## Конфигурация

Оба контура по умолчанию выключены. `appsettings.json` загружается из
каталога приложения. При `Enabled=false` не привязываются даже некорректные
неиспользуемые реквизиты соответствующего контура. При включении настройки
проверяются до создания сетевых клиентов; ошибка имеет безопасное сообщение.

Для включённого приёмника оператор задаёт переменными окружения:

- `Telegram__Enabled`, `Telegram__AutoStart`;
- `Telegram__ApiId`, `Telegram__ApiHash`, `Telegram__PhoneNumber`;
- абсолютные, различные `Telegram__SessionPath`, `Telegram__UpdateStatePath`,
  `Telegram__ChannelsPath` вне исходников, `.git`, публикации и `bin/obj`;
- положительные `Telegram__QueueCapacity` и `Telegram__MaxChannels`.
  Эксплуатационные размеры намеренно не выбраны;
- `Telegram__ControlPeerKind` (`User`, `Chat`, `Channel`) и положительный
  `Telegram__ControlPeerId`: внутренний MTProto ID, полученный из доступных
  диалогов, с соответствующим `access_hash`, без Bot API-префикса `-100`;
- при необходимости `OperationTimeout`, `ForwardTimeout`, `DrainTimeout`,
  `CloseTimeout`, `CommandWaitTimeout` с префиксом `Telegram__`.
  `ForwardTimeout` не должен превышать `DrainTimeout`.

`OutboundProxyUrl` с непустым значением отклоняется. Первую авторизацию
приложение не предоставляет: нужна заранее сохранённая пользовательская
сессия, полученная отдельной безопасной процедурой владельца. Отсутствие
сессии, запрос кода/пароля или отказ авторизации дают `AuthorizationRequired`.
Реальные реквизиты и сессии в репозитории отсутствуют. Одну сессию нельзя
одновременно использовать российским и европейским экземплярами.

Для отдельного управляющего бота нужны `EuropeTelegramBot__Enabled`,
`EuropeTelegramBot__BotToken`, положительный числовой
`EuropeTelegramBot__OwnerUserId`. Управляются также `PollTimeoutSeconds`,
`RequestTimeout`, `RetryDelay`, `MaxConsecutiveFailures` с тем же префиксом.
HTTP timeout должен превышать timeout long polling. Бот не создаёт webhook
и не открывает веб-порт. Уже установленный webhook — внешний отказ;
приложение его самостоятельно не удаляет.

Команды личного чата владельца:
`/start_receiver`, `/stop_receiver`, `/status`, `/channels`,
`/add_channel <username>`, `/remove_channel <username>`, `/help`.
Группы и посторонние пользователи игнорируются. Бот использует один контроллер
приёмника и отдельный от пользовательской сессии токен.

## Каталог и фильтрация

Формат каталога — `{ "Version": 1, "Channels": ["public_name"] }`.
Имена — ASCII, 5–32 символа, начинаются с буквы; входное `@` удаляется,
регистр нормализуется. Проверяется основное публичное имя доступного
`broadcast`-диалога; автоматического вступления в каналы нет.
Источник нельзя одновременно назначить контрольным broadcast-получателем:
это исключает обратную подачу собственных пересылок в приём.

Отсутствующий каталог означает первоначальный пустой список. Повреждённый,
неподдерживаемый, слишком большой каталог или дубли имён дают отказ;
такой файл не заменяется пустым. Чтение/запись используют JSON source generation.
Запись идёт в один соседний файл `<ChannelsPath>.tmp`, затем flush и rename
с заменой. Рабочий снимок заменяется только после успешного rename.
При сбое собственный временный файл удаляется. Остаток `.tmp` после аварии
требует проверки оператором; повторная запись его молча не перезаписывает.
Гарантия переживания потери питания не заявлена.

Принимаются только новые текстовые `UpdateNewMessage`/`UpdateNewChannelMessage`
из разрешённых broadcast-каналов, с UTC-временем Telegram позднее полной
готовности текущего поколения. Правки, история, группы и медиа без текста
не принимаются. Очередь содержит неизменяемые `TelegramChannelPost`, без TL-объектов.

## Владение и остановка

`TelegramReceiverController` владеет состоянием, снимком допуска, одним
`Channel<TelegramChannelPost>`, CTS и одним потребителем поколения.
`Start/Stop/Add/Remove` сериализованы конечным ожиданием `SemaphoreSlim(1,1)`.
Порядок коротких блокировок: controller → session; сеть/Dispose не выполняются
под ними. Callback только преобразует update и вызывает `TryWrite`.

`TelegramAccountSession` владеет одним `WTelegram.Client`, `UpdateManager`,
подписками и peer-адресацией. Проверка каналов не публикует новый снимок до
записи каталога. Peers удалённых каналов удерживаются только для уже принятых
публикаций, затем освобождаются; размер ограничен активными каналами и очередью.
Пересылка помещена в эту роль, отдельный `TelegramOriginalForwarder` не нужен.

Start создаёт новое поколение только после завершения прежнего. Повторный
Start в Receiving — `AlreadyApplied`; незавершённая очистка — `Conflict`.
Пустой список допускает авторизованную сессию для дальнейшего Add.
Add без текущего приёма/авторизованного соединения — `Unavailable`.
Повторные Add/Remove и Stop определены идемпотентно.

Stop закрывает допуск, завершает writer, даёт потребителю срок `DrainTimeout`,
затем закрывает клиент и сохраняет update state в порядке библиотеки:
`DisposeAsync` → наблюдение незавершённых RPC → `SaveState`.
Синхронный `SaveState` является границей внешней библиотеки; операция закрытия
зарегистрирована и имеет отдельный срок ожидания. При превышении сроков статус
содержит `ShutdownTimeout`, незавершённое дренирование и возможные потери;
незавершённая сессия/потребитель блокируют новый Start. Повторный Stop ждёт
то же закрытие, не создаёт второй Dispose. Если освобождение клиента завершилось
исключением, очистка остаётся ошибочной; безопасное освобождение не утверждается.

`EuropeTelegramRuntime` наблюдает сигналы отказа и закрывает контур при
остановке хоста. `EuropeTelegramBot` владеет HTTP-клиентом и poller; хост
останавливает его первым. Отказ Bot API даёт `BotUnavailable` без уничтожения
пользовательской сессии. После Stop приёмника бот продолжает принимать команды.

Очередь: `BoundedChannelFullMode.Wait`, `AllowSynchronousContinuations=false`,
один reader, несколько потенциальных writers. Полный канал немедленно возвращает
`TryWrite=false`: растут счётчики overflow/возможной потери, приём переходит
в Error, а очистку выполняет владелец, вне callback. Потерянный пост не скрывается.

Один потребитель пытается `ForwardMessagesAsync(..., drop_author:false)`
через MTProto; защищённые оригиналы и недоступный peer дают видимый отказ.
Нет текстовой копии от Bot API и зависимости от LLM. Успех считается только
при наличии подтверждённого Message ID. Автоматических повторов пересылки нет;
при таймауте реальный RPC может иметь неизвестный результат. `WaitAsync` не
отменяет физический запрос; сессия помечается непригодной, закрытие и RPC
остаются учтены. Отмена команды с активным RPC также завершает это поколение.

## Телеметрия и разрешённые проверки

`ILogger`/`LoggerMessage` фиксируют отказы и переходы, без успешного журнала
каждой публикации, исходного текста, токенов и сырых исключений.
`IMeterFactory` владеет Meter; метрики имеют только ограниченные теги операции,
исхода/категории/состояния. `ActivitySource` освобождаются владельцами.
Корреляция публикации — ChannelId/MessageId в техническом логе/trace.

Все команды сборки выполняются из `europe/`:

```powershell
dotnet --version
dotnet restore .\ProjectTraiding.Europe.slnx
dotnet build .\ProjectTraiding.Europe.slnx -c Release --no-restore
dotnet publish .\src\ProjectTraiding.Europe\ProjectTraiding.Europe.csproj -c Release -r win-x64 -p:PublishAot=true
```

Release build завершён без предупреждений. Windows Native AOT с C++ toolchain
скомпилирован, но имеет `IL2104/IL3053` обеих Telegram-библиотек.
Раскрыты `IL2026/IL3050`, дополнительно `IL2067` (TL) и `IL2072` (Telegram.Bot).
Предупреждения не подавлены, reflection JSON и PublishAot не отключены.
Активная работа обеих библиотек в AOT не подтверждена, в том числе сериализация
при `JsonSerializerIsReflectionEnabledByDefault=false`.

Linux Native AOT из Windows не выполнялся. В установленном WSL/Ubuntu нет
обнаруженных SDK dotnet, clang и заголовков zlib/libc; среда сборки не готовилась.
Debian 13 не проверен. Бинарные файлы не запускались.

## Соответствие правилам v0.2

- № 1–14: собственных интерфейсов, фабрик, универсальной шины и хранилищ нет.
  Session закрывает причины 1/2/3 правила 13; Catalog — 1/3; Controller — 1/2;
  Bot — 1/2/3. Runtime — содержательная hosted-роль, handler/parser и LoggerMessage
  статические. Новых типов `*Service/*Manager/*Helper/*Utils` нет.
- № 6: именованные делегаты требуются WTelegram callbacks; единственная лямбда
  — холодная настройка штатного `HostOptions`. Горячих замыканий/LINQ нет.
- № 8: публикация — неизменяемый ссылочный объект с семью полями; крупный struct
  не используется. Производительность без замеров не заявлена.
- № 19–28: внешние ошибки типизированы и санитизированы; timeout/retry учитываются
  на границе. Bot API имеет одну последовательную физическую cadence, внутренние
  retries/redirects выключены, число повторных сбоев ограничено с RetryAfter.
  MTProto flood retry/reconnect выключены. Платформенный IDisposable.Dispose
  не получает token; синхронные файловые metadata/rename и библиотечный SaveState
  не имеют async API. Содержимое каталога читается/пишется асинхронно.
  После начала Stop очистка конечна и принадлежит владельцу, независимо от отмены
  вызывающей команды; это сохраняет инвариант ресурсов.
- № 29–30: SQL, PostgreSQL и Writer отсутствуют по границе задачи.
- № 31–38, 41–42: включённая конфигурация проверяется, ресурсы/накопление ограничены,
  время явно UTC, идентификаторы целые; собственная JSON-сериализация с source gen.
- № 18, 39–40: применяется `.editorconfig`, но format, тесты и замеры не запускались
  по прямому запрету владельца для этого цикла.
- № 3, 37: предупреждения внешних библиотек сохранены и раскрыты; AOT-приёмка
  требует будущего решения/проверки. Чужие библиотеки не исправлялись и не обновлялись.

Других известных отклонений по статическому чтению не выявлено.
Поведенческие инварианты запуском не подтверждены. До промпта № 7 нет
устойчивого хранения публикаций и гарантии сохранности при аварии.
