# Задание агенту: приёмник публикаций Telegram

**Основание:** `Telegram_Architecture_v1_2_2.md`.  
**Репозиторий:** `ForPMService/ProjectTraiding`, исходное состояние — `main`.  
**Тип работы:** реализация инфраструктурного модуля, не изменение архитектуры и не разработка `CustomFeatures.News`.

## 1. Цель и критерий готовности

`ProjectTraiding.Api` с `Telegram:Enabled=true` авторизует один пользовательский Telegram-аккаунт, сопоставляет несколько настроенных каналов и получает **новые текстовые публикации** через `WTelegramClient`.

Результат виден через `ILogger`: для каждого принятого сообщения известны канал, идентификатор публикации, исходный текст и два времени. Полный текст журналируется **только в Development**.

**Принято**, если вручную подтверждены вход, повторный запуск без кода, получение нового поста из каждого настроенного канала, отклонение постов посторонних каналов и независимая работа `Api`/`Moex` при проблемах Telegram. Если живое соединение недоступно, этот пункт **не отмечать выполненным**.

В первом этапе: **нет** вызова LLM, `CustomFeatures.News`, записи в PostgreSQL, исторической загрузки и реализации прокси.

Проверить это повторно перед изменением.

## 3. Обязательные ограничения

1. Один `TelegramAccountSession` как `Singleton` на процесс, внутри один `WTelegram.Client`. Маршруты входа и фоновая служба обращаются к одному объекту.
2. Для приёма публикаций использовать только `WTelegramClient`. **Существующий пакет `Telegram.Bot 22.10.3.2` оставить в `.csproj` без изменений**; типы и клиенты `Telegram.Bot` в новом коде не использовать. Будущие уведомления и команды не реализовывать.
3. `Api` — точка сборки. `Telegram` не ссылается на `Moex`, `Management` или `CustomFeatures`.
4. `Enabled=false` по умолчанию: клиент не создаётся, вход и сетевой приём не запускаются; статус возвращает `Disabled`.
5. Первый вход выполняется **в работающем `Api`**, в Development и Release, без внешней консольной программы.
6. `SessionPath` и `UpdateStatePath` — абсолютные пути в постоянном каталоге вне Git и каталога публикации. Одновременная работа двух процессов с одним файлом сессии не поддерживается.
7. Прокси **не реализовывать**: `OutboundProxyUrl=null` — прямое соединение; непустое значение — конфигурационная ошибка Telegram без подключения напрямую. Не задавать глобальные `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`; не вводить `TcpHandler`, `MTProxyUrl`, VPN и не изменять клиентов `Moex`.
8. Ошибки Telegram не останавливают `Api` и существующие фоновые службы `Moex`. Не менять глобальный `BackgroundServiceExceptionBehavior`.
9. Не писать серверные тесты. Не добавлять ORM, прикладную рефлексию, собственные интерфейсы на одну реализацию, LINQ в обработчике сообщений, собственные делегаты для выбора прикладного поведения. **Штатный callback `Func<TL.Update, Task>` для `WithUpdateManager` разрешён и необходим для работы библиотеки.**
10. Не отключать `PublishAot` или запрет сериализации через отражение; не менять инфраструктуру или схему PostgreSQL.

## 4. Минимальные объекты и ответственность

| Компонент | Ответственность |
|---|---|
| `TelegramOptions` | Конфигурация `Enabled`, `ApiId`, `ApiHash`, `PhoneNumber`, `SessionPath`, `UpdateStatePath`, `Channels`, `OutboundProxyUrl` |
| `TelegramAccountSession` | Создание/владение одним клиентом, пошаговый вход, текущее состояние, ожидание авторизации, освобождение клиента |
| `TelegramChannelReceiverService : BackgroundService` | Старт после включения, ожидание входа, загрузка каналов, разрешение потока, штатное завершение |
| `TelegramUpdateHandler` | Проверка одного `TL.Update`, преобразование разрешённых сообщений, журнал |
| `TelegramChannelPost` | Семь технических полей публикации, без типов WTelegram в контракте |
| `TelegramServiceCollectionExtensions` | `AddTelegram(builder.Configuration)` |
| `TelegramAuthorizationEndpoints` в `Api` | Только локальные `GET /telegram/auth/status` и `POST /telegram/auth/answer` |
| `TelegramAuthJsonContext` в `Api` | Генерация JSON-метаданных для тел этих маршрутов, независимо от `ManagementJsonContext` |

Не создавать дополнительные уровни, интерфейсы, фабрики, очереди и хранилища ради будущих сценариев.

## 5. Настройки и авторизация

Обычный `appsettings.json` содержит только включение, пути, публичные имена каналов и `OutboundProxyUrl=null`. `ApiId`, `ApiHash` и `PhoneNumber` поступают из User Secrets при локальной работе и секретов окружения при поставке. Одноразовые коды и пароль 2FA не сохранять ни в один конфигурационный источник.

Начальная последовательность:

```text
Enabled=true
→ проверить обязательные настройки, абсолютные пути и неподдерживаемый OutboundProxyUrl
→ создать единственный WTelegram.Client(apiId, apiHash, sessionPath)
→ зарегистрировать WithUpdateManager(callback, updateStatePath) ДО авторизации
→ Client.Login(phoneNumber)
   ├─ null → Authorized
   ├─ verification_code → VerificationCodeRequired
   ├─ password → PasswordRequired
   ├─ email → EmailRequired
   ├─ email_verification_code → EmailCodeRequired
   └─ name → Error: регистрация нового аккаунта не поддерживается
```

Последующий ввод из `POST /telegram/auth/answer` передаётся **тому же** `Client.Login(value)`. Каждый результат снова интерпретируется по приведённой схеме. Сохранённая действующая сессия должна позволять повторный запуск без кода.

Обязательное поведение:

- `GET /telegram/auth/status` **не создаёт нового клиента и не инициирует авторизацию**. Только читает уже существующее состояние.
- `POST /telegram/auth/answer` допустим только при ожидаемом типе ввода, непустом `value` и единственной активной последовательности входа.
- Повторный или параллельный ввод не создаёт нового клиента и не вызывает `Login` одновременно. Отклонить такой запрос понятным результатом; сериализовать операции продолжения входа.
- При неверном коде или исключении показать безопасный статус/ошибку **без значения кода**; не выполнять повторную регистрацию аккаунта и не выдавать `Authorized` до подтверждения от библиотеки. Не придумывать бесконечные повторы.
- Ожидание ввода **асинхронное**; не вызывать `Console.ReadLine`, не блокировать поток и не задерживать старт `Api`.
- Ошибка конфигурации или входа фиксируется как ошибка Telegram. Необработанное исключение не должно завершать весь host.

### Маршруты первой авторизации

Только:

```text
GET  /telegram/auth/status
POST /telegram/auth/answer
```

- Работают и в Development, и в Release.
- Проверяют **реальный** `HttpContext.Connection.RemoteIpAddress` через `IPAddress.IsLoopback`, а не `Host` или доверие к `X-Forwarded-For`. Нелокальное обращение получает `403` до выполнения операции.
- Ожидаемое использование Release — через SSH-туннель к существующему локальному HTTP-интерфейсу `Api`. Второй сокет/порт Kestrel и серверный сертификат **не** добавлять.
- При публичном обратном прокси, передающем трафик в Kestrel с loopback, такая схема **не является безопасной**. Не реализовывать поддержку такого развёртывания в этом задании и не утверждать, что фильтр по адресу защищает от него.
- Тело `POST`, `value`, пароль, коды и конфигурационные секреты не записывать в приложение, HTTP-журнал и исключения; в ответе разрешены только состояние и имя ожидаемого поля. `GET` при `Enabled=false` возвращает `Disabled`; `POST` при выключенном модуле не создаёт клиента.
- Тела ответа и запроса сериализовать через собственный `TelegramAuthJsonContext`; регистрировать в `TypeInfoResolverChain`, не нарушая существующий `ManagementJsonContext`.

## 6. Загрузка каналов и момент готовности

После `Authorized`:

1. `Messages_GetAllDialogs()` — актуальные диалоги одного аккаунта.
2. `CollectUsersChats(manager.Users, manager.Chats)` — заполнить сведения о чатах и каналах.
3. Для каждого `Channels[]` найти уже доступный аккаунту **публичный канал публикаций** по `username` без `@`, без учёта регистра.
4. Различать канал публикаций и супергруппу: в MTProto оба представлены `TL.Channel`, но для публикационного канала требуется признак `broadcast`.
5. Построить словарь `channelId → username/title`; извлекать идентификатор канала из `TL.PeerChannel`. **Не добавлять `-100`** из Bot API.
6. Если хотя бы один канал не сопоставился, вывести его имя в ошибке, установить `Error`, не включать выдачу публикаций; `Api` и `Moex` продолжают работу.
7. Зафиксировать `readyAtUtc` **после** полного сопоставления каналов, затем установить `Receiving`.

`UpdateManager` зарегистрирован до входа и может получить прежние неподтверждённые updates. **До `Receiving` не выдавать сообщения наружу.** При `Receiving` не выдавать публикации, у которых время публикации не позже `readyAtUtc`. У Telegram время сообщения имеет секундную точность; не считать публикации из той же секунды гарантированно новыми. Это сознательное ограничение наблюдения первого этапа; восстановление пропущенных постов до готовности здесь не требуется.

Данные `UpdateManager.SaveState` не содержат словарей `Users/Chats`; после каждого перезапуска заново выполнять шаги 1–5.

## 7. Обработка сообщений

Обработчик принимает только:

```text
UpdateNewMessage (включая UpdateNewChannelMessage)
  → TL.Message, не TL.MessageService
  → peer_id является PeerChannel
  → channelId в разрешённом словаре
  → канал относится к broadcast
  → TL.Message.message не пустой
  → Receiving и PublishedAt > readyAtUtc
  → TelegramChannelPost
  → ILogger
```

Пропускать правки, удаления, реакции, служебные сообщения, личные сообщения, группы и медиа без текста. Не скачивать файлы и не выполнять очистку/склейку/классификацию.

`TelegramChannelPost` содержит **только**:

| Поле | Тип |
|---|---|
| `ChannelId` | `long` |
| `ChannelUsername` | `string?` |
| `ChannelTitle` | `string` |
| `MessageId` | `int` |
| `Text` | `string` |
| `PublishedAt` | `DateTime` |
| `ReceivedAt` | `DateTime` |

`PublishedAt` берётся из `TL.Message.date`, `ReceivedAt` фиксируется при обработке принятого обновления. Оба значения в UTC; при диагностике выводить `DateTime.Kind`. Не подменять неизвестную временную зону простым `SpecifyKind(Utc)` без проверки фактической семантики. Не переводить в московское стенное время.

В `Development` писать исходный `Text` полностью; в Release — только технические поля без текста. Не включать в объект `source`, `known_at`, `secid`, `event_type`, данные агента или оценок.

## 8. Жизненный цикл и ошибки

- `TelegramAccountSession` — единственный владелец экземпляра `WTelegram.Client` и данных авторизации.
- `TelegramChannelReceiverService` запускает приём только после авторизации, сопоставления каналов и выставления состояния `Receiving`.
- При штатной остановке приложения прекратить выдачу событий, корректно освободить клиент и сохранить `UpdateManager.SaveState(UpdateStatePath)` в рекомендованном библиотекой порядке. Файлы не размещать под каталогом публикации.
- Если соединение, конфигурация или поиск каналов завершились ошибкой, закрыть ресурсы Telegram и установить безопасный статус `Error`; не завершать `Api`, не менять общую политику host. Для новой попытки после такого отказа в первом этапе допустим перезапуск `Api`.
- Не обещать доставку «ровно один раз» и не добавлять собственный повторный опрос или восстановление исторических сообщений.

## 9. Порядок коммитов и доказательства

Работать в отдельной ветке. **Один логический шаг — один коммит. Каждый коммит должен собираться сам.** Не называть незапущенную проверку успешной.

### Коммит 1. Каркас и привязка к `Api`

**Было:** Telegram-проект не связан с `Api`; подключены обе библиотеки.

**Стало:** оба пакета (`Telegram.Bot 22.10.3.2` и `WTelegramClient 4.4.9`) сохранены; для текущего приёма используется только `WTelegramClient`; добавлены `TelegramOptions`, `AddTelegram(...)`, ссылка `Api → Telegram` и вызов регистрации в `Program.cs`. При `Enabled=false` не создаётся клиент и нет сетевых операций. Не добавлять фиктивную авторизацию или приёмник, который пока ничего не делает.

**Проверка:**

```powershell
dotnet build backend/ProjectTraiding.slnx
dotnet publish backend/src/ProjectTraiding.Api/ProjectTraiding.Api.csproj -c Release
```

На этом шаге публикация — **ранняя проверка NativeAOT** после включения Telegram-проекта с обоими существующими пакетами в граф зависимостей; она ещё не доказывает готовность последующего приёмника. Если проблема была в проекте до правок или отсутствует инструментальная цепочка AOT — указать это отдельно и приложить вывод. Не отключать `PublishAot`.

### Коммит 2. Единый клиент и авторизация через `Api`

**Было:** нет входа и маршрутов авторизации.

**Стало:** есть единственный `TelegramAccountSession`, последовательность `Client.Login`, состояния входа и два локальных маршрута. Вход не требует отдельной программы. `UpdateManager` регистрируется до `Login`; пока нет рабочего приёмника, callback не выдаёт публикации (без предварительной обработки сообщений).

**Проверка:**

```powershell
dotnet build backend/ProjectTraiding.slnx
```

Проверить вручную: `Enabled=false → Disabled, без клиента`; нелокальный запрос → `403`; при первом входе статус требует код; ответ продолжает тот же вход; повторный запуск с сохранённой сессией не требует код. Если Telegram недоступен напрямую — зафиксировать сетевой блокер, **не утверждать**, что вход проверен.

### Коммит 3. Сопоставление каналов и приём публикаций

**Было:** авторизация имеется, выдачи публикаций нет.

**Стало:** одна фоновая служба, поиск выбранных `broadcast`-каналов, фильтр обновлений, `TelegramChannelPost`, журналирование и `SaveState`.

**Проверка:**

```powershell
dotnet build backend/ProjectTraiding.slnx
dotnet publish backend/src/ProjectTraiding.Api/ProjectTraiding.Api.csproj -c Release
```

Ручная приёмка там, где **прямое** соединение с Telegram доступно:

1. Telegram выключен → другие контуры работают, клиента нет.
2. Первый вход через `Api`, код и пароль не попадают в журнал; файл сессии создан по заданному пути.
3. Повторный запуск с тем же файлом — вход без повторного кода.
4. Нелокальный запрос к обоим маршрутам отклоняется.
5. Все настроенные каналы разрешены как `broadcast`, ни один не подменён супергруппой.
6. Новый текстовый пост **из каждого выбранного канала** виден в журнале с верными `ChannelId`, `MessageId`, каналом, исходным текстом в Development и обоими временами с `Kind`.
7. Пост из постороннего канала, правка, пустое и служебное сообщение не выходят из модуля.
8. Старый пост, доставленный после авторизации, не считается новым.
9. Отсутствие настроенного канала останавливает только Telegram-приёмник.
10. Непустой `OutboundProxyUrl` не запускает прямое соединение и не создаёт Telegram-клиент.
11. Нет обращений к LLM, `CustomFeatures.News` или таблицам PostgreSQL.
12. На Release-публикации `PublishAot` не отключён. Если публикация не проходит — ошибка приведена полностью, этап **не объявляется технически завершённым**.

## 10. Отчёт агента после каждого коммита

Короткий отчёт обязателен:

```text
Коммит: <hash>
Изменено: <перечень фактических файлов>
Было → стало: <проверяемая разница>
Запущено: <команды>
Результат: <фактический вывод и код завершения>
Ручная проверка: <подтверждена / не выполнялась / блокер>
Ограничения: <что остаётся непроверенным>
```

Если проверка не прошла, агент сообщает конкретный сбой и **не маскирует его общим утверждением «готово»**. Не подменять живое получение публикации сборкой проекта. Не расширять задание на прокси, инфраструктуру LLM, `Moex` или PostgreSQL без отдельного согласования.
