# Решения архитектуры и ближайший план — v0.7

Консолидирует решения сессии. **Уточняет v0.6**: добавлен технический предохранитель Sync GET
(`no-store` + вызов только кнопкой, не ссылкой/prefetch) и ограничение на размещение sync-маршрутов
(контур `Moex`, не `Management`). По правилам глагола и контурам документ **финален** — дальше исполнение.

Принцип сквозной: **что стабильно и знаемо сейчас — делаем сейчас; ждёт только переменная часть
(хранилище рядов).** Уже воплощён в `moex_load_tasks.storage_target` (`none` → `clickhouse`).
Опирается на предохранитель минимальности (тариф — да, связи — да) и probe-first методологию.

Статус: **принят к исполнению.**

## 1. Что подтвердила сверка с кодом

Архитектура хэндоффа верна. Завышены три пункта «что сделано»:

- **Writer-логирование наполовину.** `WriteCompleted` после `CommitAsync` не вызывается; `startTs`
  мёртвый; `DateParseFailed` не используется. Успешный путь немой.
- **Правило 3.7 не реализовано.** `trade_session_date`, futures `last_trade_date`/`last_del_date`
  через `DateOnly.Parse` (fatal). Битая непустая дата уронит батч.
- **`.gitignore` обойдён.** Голое `storage/`; namespace `…Storage.Postgres` при папке `StorageBase/`.

Дополнительно: **коллизия EventId** (141/142/143 заняты `MoexLogMessages`).

Состояние рыночной диагностики (важно для A2): **парсеры готовы и нагрузочно проверены**
(`ParsingAlgUtf8` по всем kind, load-тест 16 эндпоинтов / 2.92M строк). Parsed-точки в
`AlgopackEndpoints` есть, но как артефакты прогона: захардкожены `SMLT`/`SiM6` и даты, имена
`/GetSuperCandles…`, смонтированы безусловно. Raw — через `/debug/columns-map` («удалить после»)
и probe. То есть источниковая диагностика рынка — это **параметризовать и причесать готовое**,
не писать с нуля.

## 2. Архитектурные решения (зафиксированы)

**Хост один.** `Api` — единственный процесс. `Moex` — библиотека, её endpoint-ы монтирует `Api`.

**Единственная сетевая граница — Angular ↔ Api.** Второй бэкенд-сервис с HTTP-вызовом Moex не
вводится: контуры одного процесса разделены ссылкой и namespace. «Бек для фронта» — это `Api`;
он тонкий (mapping без логики): принимает от фронта команды и возвращает результат, отдаёт чтение.

**Проекты первой очереди: `Api` / `Moex` / `Vitrine` / `Management`.** Первоочередна вся вертикаль
**управляющей модели**: источник MOEX → PostgreSQL управляющей модели → Vitrine/Management → Angular.
Рыночные ряды в эту вертикаль не входят: для них первая очередь закрывает source contract (raw/parsed),
а запись ждёт решения по хранилищу — в PostgreSQL ряды не пишутся.

**Две природы команд, один паттерн рабочей точки** (вызывающий фронта → тонкий маршрут `Api` →
операция → result-DTO):
- **MOEX-операции / sync** (bootstrap инструментов/календаря; позже — рыночная загрузка). Sync —
  это серверный fetch из MOEX + UPSERT управляющих таблиц; bootstrap = первичная полная sync.
  Операция и оркестрация — в `Moex`; маршрут монтирует `Api`. **Sync не кладём в `Management`** —
  иначе MOEX-fetch протечёт в проект операторского ввода.
- **Операторский ввод** (тарифы, связи) — в `Management`: пользовательские поля, валидация до SQL,
  FK-aware запись.

**Разделение результатов записи и контракта операции.** Writer не знает про API-контракт: возвращает
технический `DbWriteResult` (строк записано, время). Внешний `LoadResultDto` собирает операция (для
sync/bootstrap) или endpoint (для одиночной загрузки). Обязательного Operation-слоя на каждую запись не вводим.

**Рыночная загрузка реиспользует MOEX-операционный паттерн**, не Management. Паттерн на sync/bootstrap
сейчас = паттерн рядов потом.

**`Vitrine` читает PostgreSQL напрямую**, без ссылки на Moex.

## 3. Таксономия точек (по глоссарию)

| Категория | Что это | Время жизни | Гейтинг | Зовёт фронт? |
|---|---|---|---|---|
| Диагностическая | raw + parsed, сверка контракта источника (вкл. рыночные kind) | постоянна в коде | `IsDevelopment()` | нет |
| Отладочная | probe, `columns-map`, одноразовое | временна | dev / удалить | нет |
| Рабочая | Sync (GET, бесполевая синхронизация) / команда (POST, с полями) → result | постоянна | публична | да |
| Vitrine | чистое чтение из PostgreSQL (GET) | постоянна | публична | да |

Правило жизненного цикла (снимает кажущееся противоречие «постоянна» + `IsDevelopment()`):
- **Диагностическая** живёт в коде постоянно, но не публикуется в production — монтируется только в dev.
- **Отладочная** постоянно не живёт: после закрытия разведки удаляется.

Гейтинг сейчас сломан: `MapRealtimeDebugEndpoints`, `MapMoexProbeEndpoints`, `AlgopackEndpoints`
смонтированы безусловно, хотя диагностические/артефакты прогона.

## 4. Контракт для фронта и правило глагола

`LoadResultDto` (внешний результат операции) + vitrine-DTO (чтение). Внутри — `DbWriteResult` от writer'а.

**Два вида GET — фронт ничего не пишет сам.**
- **Vitrine GET** — чистое чтение из PostgreSQL.
- **Sync GET** — бесполевая синхронизация с MOEX: сервер идёт в MOEX, парсит, делает идемпотентный
  UPSERT в PostgreSQL, возвращает результат. Базу меняет не «метод фронта», а серверная операция
  синхронизации; фронт лишь вызывает заранее определённый сценарий без пользовательских данных.

**POST** — когда пользователь передаёт поля: создаёт/меняет свои данные или задаёт параметры команды
(тариф, связь; `secid/dataKind/период/storage_target`).

**Sync GET допустим, только если** все четыре:
1. пользователь не передаёт поля формы;
2. сценарий заранее определён, триггер — кнопка оператора, не фоновый планировщик (планировщик —
   другой источник команды, отложен);
3. повторный вызов безопасен для данных (UPSERT, правило 30);
4. остаточный риск принят: случайный повторный вызов (prefetch/кэш) даст лишний платный rate-limited
   запрос к MOEX — для внутреннего пульта на одного оператора это низко.

**Технический предохранитель Sync GET** (закрывает п.4 минимальной техникой, без отдельного контура):
- ответ отдаёт `Cache-Control: no-store`;
- на фронте вызывается только явным обработчиком кнопки (`fetch`), не ссылкой `<a href>`, `<img>`,
  prefetch или автопереходом.

Публичная рабочая точка (Sync GET или POST) появляется при реальном вызывающем — кнопке/форме фронта;
до этого логика остаётся внутренней операцией или dev-триггером, не публикуется.

## 5. Чего сейчас НЕ строим

- **Отдельный сетевой бэкенд-сервис** с HTTP-вызовом Moex — один процесс, хоп лишний. Angular ↔ Api
  строим; Api ↔ Moex по сети — нет.
- **Хранилище рыночных рядов и путь записи — единственный отложенный шов.** Источниковая сторона
  (raw/parsed/парсеры) закрывается сейчас; ждут только: ClickHouse, загрузчики-писатели в ClickHouse,
  логи этого контура, подключение к фронту. Типизированный шов `storage_target` уже в схеме.
- **Фоновый планировщик sync** — sync пока только операторской кнопкой; шедулер не строим.

3. Writer-проход (один, оба writer'а): счётчик строк + `WriteCompleted` после `CommitAsync`; writer

4. `LoadResultDto`: тип локально в Moex, в `AppJsonContext`. Операция (sync/bootstrap) или endpoint
   (одиночная загрузка) собирает `LoadResultDto` из `DbWriteResult`; load-ручки отдают его вместо `204`.
5. Мелочи вне writer'а: коллизия EventId (подвинуть 141–143 либо переписать «резерв»); `.gitignore`

**Блок B. Командный паттерн + наполнить постгрес.**

6. MOEX-операции (sync): bootstrap инструментов и календаря — fetch из MOEX + UPSERT, метод +
   оркестрация в Moex, сборка `LoadResultDto`. Бесполевая sync → **GET** (с предохранителем из §4),
   которую вызывает кнопка фронта (не POST, не в Management). Эталон паттерна; рыночная загрузка
   (с полями) повторит как POST.
7. `Management`: тарифы и связи — есть поля → **POST** с телом, валидация до SQL, ошибка текстом на фронт.
8. `Vitrine`: чистое чтение из PostgreSQL без ссылки на Moex — `status`, `instruments`, `calendar/off-days`,
   `broker-tariffs`, `instrument-relations`. Поля рыночного покрытия — «пока пусто».

**Блок C. Фронт.**

9. Angular-консоль подключается к рабочим точкам (B6–B7) и vitrine (B8). Глагол по полям: sync
   инструментов/календаря — GET (кнопка + явный `fetch`); тарифы/связи — POST. Постгрес наполняется и
   читается через фронт, не через ручные браузерные дёрганья.

**Блок D. Рыночная загрузка (последним — только хранилище).**

10. Решение по хранилищу → загрузчики-писатели в ClickHouse → логи контура → конечная точка
    `data-loads` (есть поля → POST) по MOEX-операционному паттерну (B6) со швом `storage_target` →
    подключение к фронту. Источник (A2) и субстрат A–C не трогаются. **Потоковая запись — по §8**
    (writer ест `IAsyncEnumerable<List<T>>` постранично, `collect` запрещён).

Блоки A и B частично независимы; контракт фронта (A3–A4) — прежде C. A1–A2 механические/чистка,
можно параллельно. A5 — гигиена, не блокирует.

## 8. Потоковая запись рыночных рядов (принцип, задел под блок D)

Не меняет глаголы и контуры — фиксирует **как** будущий ClickHouse-writer обязан принимать данные,
чтобы запрос «все ряды за несколько лет» не материализовал диапазон в память. Записано сейчас, до
написания блока D, чтобы его не реализовали через `collect` по инерции.

**Граница потока — одна страница. Поток не материализуется нигде между MOEX и ClickHouse.**

- **Клиент (готов, не трогать).** `IAsyncEnumerable<List<T>>`, `yield return` страницы, `RentedBuffer`
  арендуется и возвращается на каждой странице. Память ограничена страницей независимо от диапазона.
  Это фундамент модели (правило 25).
- **CH-writer (блок D).** Вход — **`IAsyncEnumerable<List<T>>`**. Потребляет постранично: страница →
  один batch INSERT → страница освобождается → запрос следующей. Никакого `CollectAsync`/`ToList`/
  накопления всех страниц до записи. Вход `IReadOnlyList<T>`/`List<T>` у рыночного writer'а — **ошибка**
  (это сигнал, что поток уже свернули).
- **Оркестратор цикла.** Только прокидывает поток дальше, сам не копит.
- **Endpoint загрузки — POST-команда**, возвращает **итог** (`LoadResultDto`: страниц/строк записано),
  **не данные**. Огромный ряд по HTTP наружу не течёт — он течёт MOEX → CH внутри, клиенту приходит
  сводка. Снимает и риск буферизации HTTP-ответа на миллионах строк.

**Backpressure — бесплатное следствие pull-модели.** Writer не запросит следующую страницу MOEX, пока
не записал текущую в CH. Темп чтения = темп записи, RAM ограничена одной страницей при любом диапазоне.
Ломается ровно одним способом — материализацией (`collect`/`ToList`); поэтому она запрещена в контуре
рыночной записи.

**Законный `List` — только справка (Postgres).** Инструменты/календарь: один ответ MOEX, мал, не
пагинируется → `List<T>` → UPSERT. Это не противоречие принципу, а другой класс данных. Рыночные ряды —
всегда поток.

**Diagnostic-`collect` (A2.1/A2.2) к этому не относится** — он для просмотра raw/parsed, в базу не пишет,
объём ограничен ручным `from/till` (правило 25: малый фиксированный объём → `List`).

**В промпт блока D — явный запрет:** вход рыночного writer'а — `IAsyncEnumerable<List<T>>`; `CollectAsync`/
`ToList`/`await foreach … list.AddRange(page)` перед записью — ошибка, шаг остановить.
