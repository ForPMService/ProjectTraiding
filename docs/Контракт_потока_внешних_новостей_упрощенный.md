# Контракт потока внешних новостей и событий

## 1. Назначение

Контур внешних новостей входит в модуль `CustomFeatures`.

Цель первого этапа — получить реальный корпус новостей и результатов агентного разбора без предварительной склейки и сложной оркестрации.

Основной поток:

```text
получили публикацию
→ сохранили исходный текст
→ один вызов агента
→ один структурированный JSON
→ проверили JSON
→ одной транзакцией записали анализ, факты и оценки
```

Склейка повторных публикаций и одинаковых фактов в первый этап не входит. Она проектируется позже по фактическим данным.

---

## 2. Общий поток

```text
Telegram API
Bigdata API
другие источники
        │
        ▼
адаптер источника
        │
        ▼
custom_features_news_publications
        │
        ▼
AgentClient
        │
        ├── постоянный промпт
        ├── разрешённые event_type
        ├── существующие global_event
        ├── разрешённые инструменты и их контекст
        ├── raw_text
        └── web search только в разрешённом режиме
        │
        ▼
LLM
        │
        ▼
один JSON
        │
        ▼
Writer
        │
        ├── custom_features_news_analyses
        ├── custom_features_news_global_events при необходимости
        ├── custom_features_news_facts
        └── custom_features_news_fact_instrument_assessments
        │
        ▼
один COMMIT результата анализа
```

Публикация сохраняется при приёме отдельно от результата агентного анализа, чтобы ошибка LLM не приводила к потере исходной новости.

После этого на одну публикацию выполняется один агентный вызов и одна транзакция записи результата.

---

## 3. Источники

Система поддерживает несколько внешних источников:

```text
Telegram API
Bigdata API
другие API
```

Для каждого источника существует свой клиент или адаптер.

После адаптера все публикации приводятся к единому внутреннему формату.

Источник является параметром.

---

## 4. Публикация

### Таблица

```text
custom_features_news_publications
---------------------------------
id
source
raw_text
published_at nullable
received_at
known_at
```

Назначение полей:

- `id` — внутренний идентификатор публикации;
- `source` — источник;
- `raw_text` — исходный текст без интерпретации;
- `published_at` — время публикации из метаданных источника, если оно предоставлено;
- `received_at` — когда публикацию получила система;
- `known_at` — с какого момента публикация доступна системе.

`external_id` и `content_hash` не используются.

Публикация записывается до вызова агента.

---

## 5. AgentClient

На одну публикацию выполняется один вызов LLM.

Агент получает:

```text
1. постоянный промпт
2. разрешённые event_type
3. существующие global_event
4. разрешённые инструменты и их контекст
5. raw_text публикации
```

В живом режиме этому же вызову может быть доступен интернет-поиск.

Отдельные `FactExtractor`, `Deduplication` и `ImpactAnalyzer` на первом этапе не вводятся.

---

## 6. Постоянный промпт

Промпт задаёт:

- что считается полезной публикацией;
- что считается атомарным фактом;
- как разделять несколько фактов внутри одной публикации;
- как выбирать `event_type`;
- как выбирать существующий `global_event`;
- когда предлагать новый `global_event`;
- как определять связь факта с инструментом;
- как определять `instrument_relevance`;
- как определять `direction`;
- как определять `impact_strength`;
- когда использовать интернет-поиск;
- запрет использовать значения вне переданных справочников;
- запрет придумывать сведения без основания;
- строгую JSON Schema ответа.

Промпт версионируется.

---

## 7. Режим интернет-поиска

Режим поиска является настройкой `AgentClient`, а не полем таблиц.

### Живой режим

Для живого потока агенту доступен web search.

Модель сама решает, нужен ли поиск для конкретной публикации.

Простая публикация может быть разобрана без обращения к сети.

Если для оценки косвенного влияния не хватает контекста, агент может использовать web search внутри того же вызова.

### Исторический режим

Для исторической обработки текущий live web search не предоставляется агенту.

Историческая защита обеспечивается режимом вызова агента, а не схемой PostgreSQL.

---

## 8. Справочник типов событий

### Таблица

```text
custom_features_news_event_types
--------------------------------
code
```

Это управляемый системой словарь допустимых типов.

Стартовые примеры:

```text
sanctions
budget_tax
talks
shipping_energy
cb_communication
corporate
```

Конкретный состав определяется отдельно.

Агент получает актуальный список и может вернуть только существующий код.

Добавление нового типа означает добавление строки в справочник без изменения схемы таблиц и DTO.

---

## 9. Глобальные сюжеты

### Таблица

```text
custom_features_news_global_events
----------------------------------
id
name
```

`global_event` представляет длительный сюжет, к которому могут относиться разные атомарные факты.

Факт может существовать без глобального сюжета.

Перед вызовом агент получает существующие:

```text
id
name
```

---

## 10. Правила `global_event`

Для факта допустимы три варианта.

### Существующий сюжет

```text
global_event_id = существующий id
new_global_event_name = null
```

### Предложение нового сюжета

```text
global_event_id = null
new_global_event_name = имя
```

### Сюжет не определён

```text
global_event_id = null
new_global_event_name = null
```

Запрещено:

```text
global_event_id != null
AND
new_global_event_name != null
```

Агент сам PostgreSQL не изменяет.

Если передан только `new_global_event_name`, Writer:

```text
ищет global_event с таким name

если найден
→ использует существующий id

если не найден
→ создаёт global_event
→ получает id

→ записывает id в fact
```

`global_event.name` должен быть уникальным.

---

## 11. Разрешённые инструменты

Агент получает список разрешённых инструментов и существующий в системе контекст для них.

Минимально:

```text
secid
название
тип инструмента
базовый актив, если применимо
```

Конкретные данные берутся из существующих справочников проекта.

Новая таблица для этого не вводится.

Агент не может вернуть инструмент вне переданного списка.

---

## 12. Контракт ответа агента

Один вызов возвращает один JSON:

```text
accepted
facts[]
```

### `accepted = false`

Публикация успешно разобрана, но полезных фактов нет:

```text
accepted = false
facts = []
```

Технический сбой вызова или нарушение JSON Schema не является ответом агента `accepted = false`. Такой случай фиксирует система отдельно через `available_at = null`.

### `accepted = true`

```text
accepted = true
facts.Count >= 1
```

Каждый факт сразу содержит свои оценки по инструментам.

---

## 13. Структура `facts[]`

Каждый элемент:

```text
event_type
summary
occurred_at nullable
global_event_id nullable
new_global_event_name nullable
instruments[]
```

Назначение:

- `event_type` — тип события;
- `summary` — короткое нормализованное описание факта;
- `occurred_at` — время или дата самого события, если известно;
- `global_event_id` — существующий длительный сюжет;
- `new_global_event_name` — предложение нового сюжета;
- `instruments[]` — оценки влияния этого факта на разрешённые инструменты.

Из одной публикации может быть извлечено несколько фактов.

---

## 14. Структура `instruments[]`

Каждая оценка находится непосредственно внутри своего факта:

```text
secid
instrument_relevance
direction nullable
impact_strength nullable
```

Отдельный `fact_index` не используется.

Writer создаёт строку `fact`, получает её `id` и записывает вложенные оценки с этим `fact_id`.

---

## 15. `instrument_relevance`

Диапазон:

```text
0..1
```

Смысл:

> насколько данный факт экономически связан с конкретным инструментом.

Это не величина ожидаемого изменения цены.

Например:

```text
instrument_relevance = 1.0
impact_strength = 0.1
```

Факт напрямую относится к компании, но предполагаемое воздействие слабое.

---

## 16. `direction`

Допустимые значения:

```text
-1
0
1
null
```

`-1` — предполагаемое отрицательное воздействие.

`0` — экономическая связь есть, но направление нейтральное.

`1` — предполагаемое положительное воздействие.

`null` — направление обоснованно определить нельзя.

---

## 17. `impact_strength`

Допустимые значения:

```text
0..1
null
```

Смысл:

> предполагаемая сила экономического воздействия факта на инструмент.

Это оценка агента, а не измеренный рыночный эффект.

Шкала должна быть одинаково определена постоянным промптом.

Горизонт этой оценки должен быть отдельно зафиксирован до реализации рабочего промпта.

---

## 18. Анализ публикации

### Таблица

```text
custom_features_news_analyses
-----------------------------
id
publication_id
agent_version
accepted
available_at nullable
```

Назначение:

- `publication_id` — какая публикация анализировалась;
- `agent_version` — версия используемого промпта и конфигурации агента;
- `accepted` — содержит ли успешно разобранная публикация полезные факты;
- `available_at` — момент, когда результат анализа фактически записан и доступен системе.

`processed` не используется.

---

## 19. Состояния анализа

### Сбой вызова или проверки

```text
accepted = false
available_at = null
```

Например:

```text
LLM не ответила
ответ невозможно разобрать
ответ не соответствует JSON Schema
Writer обнаружил нарушение контракта
```

Факты и оценки не записываются.

Исходная публикация остаётся в `custom_features_news_publications`.

### Публикация разобрана, полезных фактов нет

```text
accepted = false
available_at != null
```

Агент успешно завершил разбор и вернул:

```text
facts = []
```

### Публикация принята

```text
accepted = true
available_at != null
```

Факты и их оценки успешно проверены и записаны.

---

## 20. Таблица фактов

```text
custom_features_news_facts
--------------------------
id
analysis_id
event_type
summary
occurred_at nullable
global_event_id nullable
```

Назначение:

- `analysis_id` — каким анализом получен факт;
- `event_type` — тип события;
- `summary` — нормализованное содержание;
- `occurred_at` — время или дата события, если известны;
- `global_event_id` — необязательная ссылка на длительный сюжет.

`duplicate_of_fact_id` не используется.

Склейка фактов откладывается до появления реального корпуса данных.

---

## 21. Таблица оценок инструментов

```text
custom_features_news_fact_instrument_assessments
------------------------------------------------
fact_id
secid
instrument_relevance
direction nullable
impact_strength nullable
created_at
```

`created_at` — момент готовности оценки.

На первом этапе все факты и оценки одного анализа записываются одной транзакцией, поэтому для строк результата используется один момент времени:

```text
assessment.created_at
=
analysis.available_at
```

Для каждой пары:

```text
fact_id
secid
```

допустима только одна строка:

```text
UNIQUE (fact_id, secid)
```

---

## 22. Запись результата

Writer сначала проверяет весь JSON.

Если ответ корректен, одной транзакцией выполняются:

```text
создание analysis

создание global_event при необходимости

создание facts

создание fact_instrument_assessments

установка общего available_at / created_at
```

После этого выполняется один `COMMIT`.

Частичная запись одного ответа агента не допускается.

Если проверка или запись результата завершилась ошибкой:

```text
accepted = false
available_at = null
```

факты и оценки этого анализа не считаются записанными.

Исходная публикация при этом уже сохранена отдельно.

---

## 23. Проверки Writer

### Анализ

```text
accepted = false
→ facts = []

accepted = true
→ facts.Count >= 1
```

### Факт

```text
event_type существует
в custom_features_news_event_types

global_event_id существует,
если заполнен

global_event_id и
new_global_event_name
не заполнены одновременно
```

### Инструмент

```text
secid входит
в переданный разрешённый список

0 <= instrument_relevance <= 1

direction =
-1 | 0 | 1 | null

0 <= impact_strength <= 1
или null

один secid не повторяется
в instruments[] одного fact
```

## 25. Полный жизненный цикл

```text
API источника
        ↓
адаптер
        ↓
publication
        ↓
сохранение исходника
        ↓
ОДИН вызов AgentClient
        │
        ├── промпт
        ├── event types
        ├── global events
        ├── инструменты
        ├── raw text
        └── web search при разрешённом режиме
        ↓
ОДИН JSON
        ↓
Writer
        ↓
полная проверка
        ↓
ОДНА транзакция результата
        │
        ├── analysis
        ├── global_event при необходимости
        ├── facts
        └── assessments
        ↓
COMMIT
```

## 26. Что намеренно не входит в первый этап

Не вводятся:

```text
дедупликация публикаций

дедупликация фактов

duplicate_of_fact_id

канонические facts

NEW / DUPLICATE

отдельный Deduplication agent

отдельный FactExtractor

отдельный ImpactAnalyzer

векторная база

embeddings

графовая база

экономический knowledge graph

impact_path

отдельная таблица mentions

повторный проход по уже записанным фактам
```

Эти механизмы проектируются только после накопления реального корпуса публикаций и понимания фактических типов повторов и ошибок.

---

## 27. Цель первого этапа

Первый этап должен ответить на практические вопросы:

```text
какие публикации реально приходят

сколько атомарных фактов агент извлекает

какие типы событий встречаются

как часто требуется web search

какие прямые и косвенные связи
с инструментами агент находит

где ошибается global_event

как распределяются
instrument_relevance
direction
impact_strength

какие реальные дубли встречаются

сколько стоит обработка публикации

какова задержка одного анализа
```

После накопления такого корпуса принимается отдельное решение о склейке и оптимизации потока.

---

## 28. Итог

Текущая модель первого этапа:

```text
получили
→ сохранили
→ один раз разобрали
→ при необходимости агент сам использовал web search
→ получили один строгий JSON
→ проверили
→ одной транзакцией записали
```

Это минимальный рабочий контур для проверки качества агентного разбора на реальном потоке данных.
