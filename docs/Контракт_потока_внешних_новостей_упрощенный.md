# Контракт потока внешних новостей и событий

## 1. Назначение

Контур внешних новостей входит в модуль `CustomFeatures`.

Цель первого этапа — получить реальный корпус новостей и результатов агентного разбора без предварительной склейки, собственного NLP-конвейера и сложной оркестрации.

Основной принцип:

```text
источник
→ технически передали данные в ИИ без смысловой предобработки
→ один вызов агента
→ один структурированный JSON
→ проверили JSON
→ одной транзакцией записали публикацию, анализ, факты и оценки
```

Если вызов агента не завершился валидным результатом, в предметные таблицы новостного контура ничего не записывается.

Повторный запуск выполняется заново от исходного источника или исходного файла.

Склейка повторных публикаций и одинаковых фактов в первый этап не входит. Она проектируется позже по фактическому корпусу данных.

---

## 2. Два режима обработки

Контур имеет два режима:

```text
Historical
Realtime
```

Они отличаются способом получения данных и режимом работы агента, но используют один постоянный промпт, одну JSON Schema, одни справочники, один Writer и одни таблицы PostgreSQL.

---

## 3. Исторический массовый поток

```text
исторический файл / API / выгрузка
        ↓
техническое чтение записей
        ↓
данные публикации без смысловой переработки
        ↓
AgentClient: Historical
        │
        ├── постоянный промпт
        ├── разрешённые event_type
        ├── существующие global_event
        ├── инструменты из custom_features_news_instruments и их контекст
        ├── исходный текст и метаданные публикации
        └── live web search выключен
        ↓
один JSON на публикацию
        │
        ├── вызов или JSON неуспешны
        │       ↓
        │   в предметные таблицы ничего не пишется
        │
        └── JSON валиден
                ↓
             Writer
                ↓
        одна транзакция:
        publication
        analysis
        global_event при необходимости
        facts
        assessments
```

Для массового режима допустима пакетная отправка запросов, если выбранный LLM-провайдер её поддерживает.

Техническая упаковка исходного файла в запросы не считается смысловой предобработкой.

До ИИ не выполняются:

```text
очистка текста
выделение сущностей
поиск тикеров
классификация события
расчёт тональности
расчёт веса
дедупликация
склейка
```

---

## 4. Realtime-поток

```text
Telegram API
Bigdata API
другой realtime API
        ↓
технический адаптер источника
        ↓
данные публикации без смысловой переработки
        ↓
AgentClient: Realtime
        │
        ├── постоянный промпт
        ├── разрешённые event_type
        ├── существующие global_event
        ├── инструменты из custom_features_news_instruments и их контекст
        ├── исходный текст и метаданные публикации
        └── web search доступен
        ↓
один JSON
        │
        ├── вызов или JSON неуспешны
        │       ↓
        │   в предметные таблицы ничего не пишется
        │   ошибка фиксируется в Observability
        │
        └── JSON валиден
                ↓
             Writer
                ↓
        одна транзакция:
        publication
        analysis
        global_event при необходимости
        facts
        assessments
```

Если realtime-вызов не удался, публикация в предметном контуре не сохраняется. Повторную обработку можно запустить позднее от исходного источника или отдельным ручным запуском.

---

## 5. Что находится между источником и ИИ

Между источником и ИИ нет смыслового слоя.

Допустим только технический адаптер, который:

```text
читает ответ API или строку файла
получает исходный текст
получает метаданные источника
формирует транспортный запрос к LLM
```

Он не должен понимать смысл новости, нормализовать содержание, выделять факты, искать компании, искать `secid`, ставить веса, назначать `event_type` или определять `global_event`.

Вся смысловая обработка выполняется LLM.

---

## 6. Вход AgentClient

На одну публикацию агент получает:

```text
постоянный промпт
актуальные event_type
существующие global_event
инструменты из custom_features_news_instruments и их существующий контекст
исходный текст публикации
метаданные публикации
режим Historical / Realtime
```

В `Realtime` агенту может быть предоставлен web search.

В `Historical` текущий live web search не предоставляется.

---

## 7. Постоянный промпт

Промпт задаёт:

- что считается полезной публикацией;
- что считается атомарным фактом;
- как разделять несколько фактов внутри одной публикации;
- как выбирать `event_type`;
- как выбирать существующий `global_event`;
- когда предлагать новый `global_event`;
- как определять связь факта с инструментом;
- как определять `instrument_relevance`;
- как определять `direction`;
- как определять `impact_strength`;
- когда использовать web search в realtime-режиме;
- запрет использовать значения вне переданных справочников;
- запрет придумывать сведения без основания;
- строгую JSON Schema ответа.

Промпт версионируется.

---

## 8. Режим интернет-поиска

Режим поиска является настройкой `AgentClient`, а не полем PostgreSQL.

### Realtime

Web search разрешён. Модель сама решает, нужен ли он для конкретной публикации.

### Historical

Текущий live web search выключен. Историческая защита обеспечивается режимом работы агента, а не таблицами новостного контура.

---

## 9. Справочник типов событий

```text
custom_features_news_event_types
--------------------------------
code
```

Это управляемый системой словарь допустимых типов событий. Агент получает актуальный список и может вернуть только существующий код.

Добавление нового типа означает добавление строки в справочник без изменения схемы таблиц и DTO.

---

## 10. Глобальные сюжеты

```text
custom_features_news_global_events
----------------------------------
id
name
```

`global_event` представляет длительный сюжет, к которому могут относиться разные атомарные факты.

Факт может существовать без глобального сюжета.

Для факта допустимы три варианта:

```text
global_event_id = существующий id
new_global_event_name = null
```

или:

```text
global_event_id = null
new_global_event_name = непустое имя
```

или:

```text
global_event_id = null
new_global_event_name = null
```

Одновременно заполнять `global_event_id` и `new_global_event_name` запрещено.

Пустая строка или строка только из пробелов в `new_global_event_name` является нарушением контракта.

Если передан только `new_global_event_name`, Writer должен получить существующий сюжет с таким `name` либо создать его и использовать полученный `id`.

`global_event.name` уникален.

Параллельные Historical-вызовы не должны создавать два одинаковых сюжета. Writer должен использовать атомарную операцию на основе уникальности `name` (`INSERT ... ON CONFLICT ...`) и не строить нормальный поток на возникновении `unique violation`.

---

## 11. Инструменты новостного контура

Состав инструментов, относительно которых агент выполняет оценку новостей, является отдельной управляемой сущностью `CustomFeatures.News`.

### Таблица

```text
custom_features_news_instruments
--------------------------------
secid
```

Таблица отвечает только на вопрос:

> какие инструменты сейчас должен анализировать новостной агент?

`custom_features_news_instruments.secid` имеет внешний ключ на `moex_instruments(secid)`, потому что текущий состав анализа может включать только известные системе карточки инструментов.

Таблица не дублирует карточку инструмента.

Для вызова агента система читает `custom_features_news_instruments` и по `secid` получает из существующих справочников проекта контекст инструмента.

Минимально агенту передаются:

```text
secid
название
тип инструмента
базовый актив, если применимо
```

Изменение состава не требует изменения кода:

```text
добавили secid в custom_features_news_instruments
→ следующий вызов агента получает новый инструмент

удалили secid
→ следующий вызов агента больше его не анализирует
```

Использовать `moex_realtime_subscriptions` как список новостного анализа нельзя: эта таблица принадлежит контуру `Moex` и определяет, какие рыночные данные собирает realtime-приёмник.

Исторические оценки инструмента не должны зависеть от текущего состава `custom_features_news_instruments`: внешний ключ из `custom_features_news_fact_instrument_assessments.secid` на эту таблицу не создаётся.

Внешний ключ из `custom_features_news_fact_instrument_assessments.secid` на `moex_instruments` также не создаётся, чтобы изменение текущего справочника не ограничивало сохранённую историю оценок.

---

## 12. Контракт ответа агента

Один вызов возвращает один JSON:

```text
accepted
facts[]
```

Если:

```text
accepted = false
```

то:

```text
facts = []
```

Это валидный результат: публикация разобрана, но полезных фактов нет. Такой результат записывается в PostgreSQL.

Если:

```text
accepted = true
```

то:

```text
facts.Count >= 1
```

Технический сбой вызова или невалидный JSON не является `accepted = false`. При техническом сбое предметная запись не создаётся.

---

## 13. Структура `facts[]`

```text
event_type
summary
occurred_at nullable
global_event_id nullable
new_global_event_name nullable
instruments[]
```

Из одной публикации может быть извлечено несколько фактов.

---

## 14. Структура `instruments[]`

```text
secid
instrument_relevance
direction nullable
impact_strength nullable
```

Оценки вложены непосредственно в свой факт. `fact_index` не используется.

`instruments[]` может быть пустым. Это означает, что факт признан полезным, но агент не нашёл среди текущего разрешённого состава инструмент, для которого может обоснованно сформировать оценку.

Отдельный порог `instrument_relevance` на уровне Writer не вводится: сохраняются валидные оценки, которые вернул агент.

Writer создаёт строку `fact`, получает `id` и пишет связанные оценки с этим `fact_id`.

---

## 15. Значение оценок

### `instrument_relevance`

```text
0..1
```

Насколько факт экономически связан с конкретным инструментом.

### `direction`

```text
-1
0
1
null
```

`-1` — отрицательное воздействие; `0` — нейтральное; `1` — положительное; `null` — направление обоснованно определить нельзя.

### `impact_strength`

```text
0..1
или null
```

Предполагаемая сила экономического воздействия факта на инструмент.

Это оценка агента, а не измеренный рыночный эффект. Горизонт оценки должен быть отдельно зафиксирован в рабочем промпте.

---

## 16. Таблица публикаций

```text
custom_features_news_publications
---------------------------------
id
source
raw_text
published_at nullable
received_at
known_at
```

`external_id` и `content_hash` на первом этапе не используются.

Смысл времени:

- `published_at` — время публикации, предоставленное источником, если оно достоверно известно;
- `received_at` — время получения записи адаптером; Writer не подменяет его своим `now()`;
- `known_at` — точка знания исходной публикации на временной шкале данных;
- `analysis.available_at` — операционное время записи валидного результата LLM;
- `assessment.created_at` — операционное время записи оценки.

Правило формирования `known_at`:

```text
если источник надёжно даёт published_at
→ known_at = published_at

иначе
→ known_at = received_at
```

Для Historical `received_at` должен приходить из доступных метаданных исходного корпуса, если такой момент там сохранён. Если исторический источник не содержит более раннего достоверного времени, оно не придумывается.

Для последующего расчёта признаков точкой знания исходной новости является `publication.known_at`. `analysis.available_at` и `assessment.created_at` являются операционными временами обработки и не заменяют `known_at`.

Ключевое правило:

> строка `publication` создаётся не при получении исходника, а только после валидного ответа агента, в общей транзакции результата.

Уникальности по тексту публикации нет.

Повторная успешная обработка того же исходного текста создаёт новую `publication` и новый `analysis`.

---

## 17. Таблица анализов

```text
custom_features_news_analyses
-----------------------------
id
publication_id
agent_version
accepted
available_at
```

Связь первого этапа:

```text
publication 1 ↔ 1 analysis
```

`publication_id` должен быть уникальным в `custom_features_news_analyses`.

`agent_version` формирует .NET-код, но значение идентифицирует не сборку приложения, а значимую конфигурацию анализа:

```text
модель
версия промпта
режим Historical / Realtime
значимые настройки инструментов агента
```

Конкретный формат идентификатора определяется реализацией без добавления новых колонок.

`available_at` — операционный момент, когда валидный результат записан и доступен системе.

Строка `analysis` создаётся только после валидного ответа агента.

---

## 18. Таблица фактов

```text
custom_features_news_facts
--------------------------
id
analysis_id
event_type
summary
occurred_at nullable
global_event_id nullable
```

`duplicate_of_fact_id` не используется. Склейка фактов откладывается до появления реального корпуса.

---

## 19. Таблица оценок инструментов

```text
custom_features_news_fact_instrument_assessments
------------------------------------------------
fact_id
secid
instrument_relevance
direction nullable
impact_strength nullable
created_at
```

Для каждой пары:

```text
fact_id
secid
```

допустима одна строка:

```text
UNIQUE (fact_id, secid)
```

`fact_id` связывается с `custom_features_news_facts`.

`secid` хранит инструмент, относительно которого агент сформировал оценку на момент разбора.

На `secid` этой исторической таблицы не создаётся внешний ключ ни на `custom_features_news_instruments`, ни на `moex_instruments`: последующее сужение текущего состава анализа или изменение текущего справочника не должно ограничивать уже сохранённую историю оценок.

В текущей одноэтапной модели:

```text
assessment.created_at = analysis.available_at
```

---

## 20. Writer

Writer вызывается только после получения валидного JSON.

Он проверяет весь ответ. Минимально:

```text
accepted = false → facts = []
accepted = true  → facts.Count >= 1

event_type существует

global_event_id существует, если заполнен

global_event_id и new_global_event_name
не заполнены одновременно

new_global_event_name =
null или непустая строка после Trim

instruments[] может быть пустым

secid входит в разрешённый список

0 <= instrument_relevance <= 1

direction = -1 | 0 | 1 | null

0 <= impact_strength <= 1 или null

один secid не повторяется
в instruments[] одного fact
```

После полной проверки одной транзакцией создаются:

```text
publication
analysis (ровно один для созданной publication)
global_event при необходимости
facts
fact_instrument_assessments
available_at / created_at
```

После этого выполняется один `COMMIT`.

Частичная предметная запись одного ответа агента не допускается.

---

## 21. Поведение при ошибке

### Агент не ответил

```text
нет publication
нет analysis
нет facts
нет assessments
```

Ошибка фиксируется в `Observability`.

### JSON не прошёл проверку

```text
нет предметной записи
```

Ошибка фиксируется в `Observability`.

### Агент успешно ответил, но полезных фактов нет

```text
publication
analysis accepted = false
facts = 0
assessments = 0
```

### Агент успешно ответил и выделил факты

```text
publication
analysis accepted = true
facts
assessments
```

---

## 22. Что намеренно не входит в первый этап

Не вводятся:

```text
предварительная предметная запись новости
собственный NLP-конвейер до LLM
очистка и нормализация текста до LLM
дедупликация публикаций
дедупликация фактов
duplicate_of_fact_id
канонические facts
NEW / DUPLICATE
отдельный Deduplication agent
отдельный FactExtractor
отдельный ImpactAnalyzer
векторная база
embeddings
графовая база
экономический knowledge graph
impact_path
отдельная таблица mentions
```

Эти механизмы могут появиться только после накопления реального корпуса и обнаружения конкретной задачи, которую текущая схема не решает.

---

## 23. Цель первого этапа

Первый этап должен показать:

```text
какие публикации реально приходят
сколько атомарных фактов агент извлекает
какие event_type реально нужны
какие global_event создаёт агент
как часто realtime-анализ использует web search
какие прямые и косвенные связи с инструментами агент находит
где появляются ложные связи
где пропускаются реальные связи
как распределяются instrument_relevance / direction / impact_strength
какие реальные дубли возникают
стоимость массовой исторической обработки
стоимость realtime-публикации
задержку realtime-анализа
```

По этим данным принимаются решения о следующих слоях.

---

## 24. Итоговая схема

### Historical

```text
файл / API / выгрузка
→ технически прочитали запись
→ AgentClient Historical
→ один JSON
→ Writer
→ одна транзакция PostgreSQL
```

### Realtime

```text
realtime API
→ технически получили публикацию
→ AgentClient Realtime
→ при необходимости web search внутри вызова
→ один JSON
→ Writer
→ одна транзакция PostgreSQL
```

Общий принцип:

```text
до ИИ — только транспорт
после ИИ — только проверка и запись
```

Контур первого этапа использует семь таблиц:

```text
custom_features_news_publications
custom_features_news_analyses
custom_features_news_facts
custom_features_news_global_events
custom_features_news_fact_instrument_assessments
custom_features_news_event_types
custom_features_news_instruments
```

Это минимальный рабочий контур первого этапа.
