# Принципы разработки фронтенда — v0.1

**Назначение.** Свод принципов и правил фронтенда, парный к «Правилам разработки
серверной части». Документ живой: ядро зафиксировано сейчас, новые правила
добавляются по мере того, как рождаются из реального шага или ошибки — как сложился
серверный свод.

**Как читать.** Сверху — философия (зачем). Под ней — правила как её применение
(что делать). У каждого правила короткое обоснование. Где правило ещё не выстрадано
на практике, оно помечено как предварительное.

---

## ФИЛОСОФИЯ

Та же, что на сервере, с одной заменой: вместо «не насиловать железо» —
«не насиловать браузер». Конкретные правила — следствие этих принципов.

**1. Простота и понятность важнее формальной чистоты.**
Компонент читается с первого взгляда. Без абстракций без причины, без обёрток на
единственную реализацию. «Хуже — значит лучше»: плоский понятный код выше
теоретически правильного, но запутанного.

**2. Не насиловать браузер.**
На сервере бережём процессор и память — на фронте бережём перерисовку и вес
сборки. Отсюда: сигналы как точечное обновление (перерисовывается только то место,
где изменились данные, а не вся страница); никаких тяжёлых чужих библиотек ради
мелочи; лишний код не грузится, пока не нужен.

**3. Игнорировать формально устоявшиеся практики ради лёгкости.**
Где «принятая» практика тяжелее простого решения — выбираем простое. Отдельностоящие
компоненты вместо модулей; свои компоненты вместо библиотек готовых; переменные CSS
вместо препроцессора стилей. Практика хороша не потому, что распространена.

**4. Опора на самые свежие практики.**
Берём новое и лёгкое, а не то, что по инерции пишут в большинстве примеров.
Angular 22, сигналы, новый синтаксис разметки — а не старый стиль с модулями и
тяжёлыми потоками.

**5. Гибкость для правки, а не для архитектуры.**
Гибкость означает «легко прочитать и поправить», а не «всё развязано через ссылки».
Лучше допустить дублирование, чем разводить код через делегаты, развязки и
универсальные параметры. Два простых похожих компонента лучше одного «гибкого» с
кучей условий, который страшно трогать. Простота кода выше устранения повторов.

**6. Источник данных отделён от отображения.**
Компонент показывает то, что лежит в сигнале, и не знает, откуда данные пришли:
обычным запросом, постоянным соединением (веб-сокет), сигналом сервера или удалённым
вызовом. Канал меняется — компонент нет. Сегодня запрос за списком, завтра поток
котировок; таблица и там и там просто рисует содержимое сигнала. Каналы подключаются
легко и не протекают в разметку.

**7. Устойчивость к молчащему серверу.**
Фронт и сервер — две отдельные программы по разные стороны сети. Сервер может не
ответить или вернуть ошибку. Фронт от этого не падает, а показывает честное
состояние. Это серверное «думать о путях ошибки, а не только об успехе» —
на фронте.

**8. Тема живая, дисциплина сквозная.**
Цвета и вид — на переменных CSS, меняются на лету. Один цвет — одно место. Тонкий
сквозной срез с зелёным прогоном между шагами.

## ПРАВИЛА (применение философии)

### Блок 1. Тема и стили

**1.1. Цвет и размер — только через переменную темы.**
В компонентах пишем `var(--accent)`, никогда не вшиваем `#6366F1` в разметку.
*Обоснование:* один цвет в одном месте — поменял токен, перекрасилось всё; иначе
правка цвета превращается в поиск по сотне мест (живой урок из кода Make).

**1.2. Живая тема — на переменных CSS, не SCSS.**
Тему (цвета, светлый/тёмный режим) ведём через `var(--...)`. SCSS — слой сборки
поверх (вложенность, миксины), но не источник цветов.
*Обоснование:* переменная SCSS исчезает при сборке, переменная CSS живёт в
работающем приложении и позволяет переключать тему без пересборки.

**1.3. Стиль одного компонента — рядом с компонентом.**
Общие токены — в глобальной теме; конкретные стили — в `.scss`-файле компонента.
*Обоснование:* стиль живёт там же, где разметка, которую красит — проще找ить и
править.

### Блок 2. Компоненты

**2.1. Компонент появляется, когда нужен.**
Не заводим компонент, папку, переменную впрок.
*Обоснование:* YAGNI — то же правило, что на сервере; преждевременная структура
мешает, а не помогает.

**2.2. Отдельностоящие компоненты, без модулей.**
Каждый компонент сам объявляет свои зависимости.
*Обоснование:* меньше церемоний, ближе к «без абстракций без причины»; это и
есть свежая практика Angular 22.

**2.3. Дублирование допустимо, развязки — нет.**
Лучше два простых похожих компонента, чем один универсальный с параметрами и
условиями.
*Обоснование:* принцип 5 — гибкость для правки; читаемость выше устранения
повторов.

**2.4. Колонку/блок без источника не рисуем.**
Если у поля нет адреса сервера в блоке C — его в разметке нет (см. карту экранов).
*Обоснование:* YAGNI плюс честность интерфейса — не обещаем данных, которых нет.

### Блок 3. Связь с сервером

**3.1. Источник данных — за службой, не в компоненте.**
Обращение к серверу живёт в отдельной службе; компонент берёт готовые данные из
сигнала.
*Обоснование:* принцип 6 — канал (запрос, веб-сокет, вызов) можно сменить, не
трогая компонент.

**3.2. Каждый экран с данными имеет состояния: загрузка, пусто, ошибка.**
Не только «успех». Пустой результат и молчащий сервер — это нормальные состояния,
а не сбой.
*Обоснование:* принцип 7 — устойчивость к молчащему серверу; это пять состояний
из спецификации страниц.

**3.3. Сервер не трогаем со стороны фронта.**
Всё общение — через посредник разработки и публичные адреса витрины/менеджмента.
Фронт не знает внутреннего устройства сервера.
*Обоснование:* единственная сетевая граница Angular ↔ Api; две отдельные программы.

**3.4. Ошибку валидации сервера показываем дословно.**
Команды (`POST`) при отказе возвращают 400 с готовым русским текстом — показываем
его, не сочиняя свой.
*Обоснование:* источник истины об ошибке — сервер; фронт не дублирует его правила.

### Блок 4. Дисциплина

**4.1. Тонкий сквозной срез.**
Один логический шаг — одна проверка сборки и зелёный прогон, потом коммит.
*Обоснование:* то же, что на сервере; ошибка ловится локально, на одном шаге.

**4.2. Типы — для нас, не для браузера.**
Пишем типы щедро: они ловят ошибки на этапе написания и в браузер не попадают
(срезаются при сборке).
*Обоснование:* типы бесплатны для веса сборки; беречь надо код и библиотеки, не
типы.

**4.3. Лишний код не грузим сразу.** *(предварительное — применим, когда экранов станет много)*
Экран грузится, когда на него зашли, а не всё приложение разом (ленивая загрузка).
*Обоснование:* принцип 2 — не насиловать браузер; дорог код, а не типы.
